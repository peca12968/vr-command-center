# 玩家參戰快照

## 單場 VR 追蹤開場

控制台 0.31.200 在個別 VR 場次連上 `GameServer` 來源後，將開場按鈕顯示為「確認追蹤並開始」。先從名冊確認各席姿態，再按開始。獨立場可由本房房控或主控操作，合併場由主控操作。

管理服務會在執行時重新核對同一串流的最新準備畫格。畫格須是 tick 0、追蹤資料在 1.5 秒內、已套用現在的管理序號，且原名冊每席已連線並具有效 `Tracked` 姿態。若有人換入場身分或在按開始前中斷，場次會保持準備中。畫面會隨快照失效撤下已就緒的訊息。

直接呼叫 `POST /api/sessions/{id}/commands` 時，可在 `Begin` 與原 `expectedSequence` 帶入 `requireTrackedStart: true`。追蹤未就緒回傳 HTTP 409 和 `tracked-vr-start-not-ready`。已套用命令可用原命令 ID 與相同本文重送。桌面排演使用「開始任務」。五房滿席追蹤開場可一併核對五房及 25 席。 [五房操作](#五房追蹤驗收開場)

管理包 0.31.201 會記錄單場追蹤開場的原始畫格，封存後可在「任務收尾」直接開啟。 [回看單場 VR 追蹤開場](SESSION_CLOSURE.md#回看單場-vr-追蹤開場)

## 從房卡查看姿態中斷快照

控制台 0.31.86 在執行中的 VR 或 MR 場次確認本房有存活席位失去有效姿態時，提供「檢視姿態中斷快照」。按鈕開啟原錄製，在該房的原畫格停住，並標示受影響席位。房控可查看本房，主控可查看五房。畫面中的已淘汰席位不列為中斷。

控制台會核對錄製來源、世界序號、管理序號及席位的原玩家，再顯示快照。按鈕只跟隨新鮮的已接受畫格。姿態恢復、場次切換、資料過期或讀取失敗時撤下入口。查看快照不會改變任務階段，暫停與繼續仍由原按鈕執行。 [即時觀戰及回放](WORLD_RECORDING.md)

控制台 0.31.87 開啟尚在錄製的快照後，會在觀戰畫面提供「返回即時觀戰」。回到原錄製時保留目前房間與鏡頭，並以新收到的畫格更新。已封存錄製可繼續逐格查看。

## MR 開場條件

控制台 0.31.12 建立的 MR 場次需要 GameServer 錄製來源。按開始時，管理服務核對最後接受的準備中快照及當前管理序號，並逐位比對名冊、入場識別、房間、席位與有效追蹤姿態。快照沿用 1.5 秒的來源新鮮度門檻。換人、管理變更或姿態中斷後，需等新快照確認再開始。

控制台 0.31.20 在「開始任務」旁顯示「MR 開場檢查」。主控可查看各房追蹤就緒人數與仍在等候的席位，房控只在此清單看到自己房間。全連線場次仍由主控開始。若快照過期、管理設定尚未同步或狀態讀取失敗，開場檢查會撤下各房就緒人數。

場次參戰快照新增 `mrStartState`。準備中的 MR 場次可回報 `EmptyRoster`、`WaitingSource`、`WaitingProfile`、`WaitingRevision`、`WaitingPlayers` 或 `Ready`。開場檢查沿用 Begin 的伺服器判定，按下開始時會依當時資料重新核對。 [驗證紀錄](PROGRESS.md#2026-11-09-mr-開場檢查與等候席位)

目前 MR 名冊支援 Quest 3。遊戲伺服器要求對應入場房間的 MR 連線設定，並拒絕桌面合成姿態。測試用追蹤快照驗證開場條件。Quest 3 實際位置、光學透視和場館對位另行驗收。 [Quest 3 部署](QUEST3.md#主控建立-mr-場次)

### 執行中追蹤

控制台 0.31.22 在 MR 執行中以橘色房卡文字提示哪些房間的存活席位尚無有效追蹤。選取場次後，「MR 執行中追蹤」會列出該房等候席位及已淘汰人數。房控在清單中查看自己房間。玩家需要重新對位時，操作員可暫停場次，再透過繼續檢查確認追蹤。

追蹤以最近接受的 GameServer MR 快照與目前名冊比對。快照逾時、來源中斷或場次切換時，畫面撤下舊的等候席位與人數，改顯示等待來源或未確認。新的有效追蹤快照抵達後才重新計數。場次參戰快照使用 `mrTrackingState`，房間總覽使用 `mrLiving` 作為存活席位分母。 [驗證紀錄](PROGRESS.md#2026-11-09-mr-執行中追蹤提示)

#### 從追蹤警示暫停

控制台 0.31.64 在房卡確認本房存活席位追蹤中斷時提供暫停按鈕。獨立場次的房控或主控可按「暫停本房重新對位」。五房合併場次由主控按「暫停五房合併場次」，確認後全場一起暫停。操作員取消時不會送出命令。

確認後，服務以原房號及場次序號重新核對最新 MR 快照。若追蹤已恢復、快照過期或管理序號已改變，命令不套用。回應失聯時可用「重試確認結果」核對原命令。一般場次暫停仍可使用。

管理端接受暫停後，房卡顯示「MR 暫停待確認」。同一遊戲來源保存了已套用該命令的有效暫停快照後，才顯示「MR 暫停已套用」。確認快照過期時會回到待確認。重新對位後，繼續前仍須通過原 MR 追蹤檢查。

### 暫停後繼續

控制台 0.31.21 在暫停中的 MR 場次顯示「MR 繼續檢查」。玩家若因追蹤中斷或原點變更需要重新對位，可在暫停中完成三點量測並回到頭盔提示的位置。主控可看到各房存活玩家的就緒人數、等候席位及已淘汰人數。房控在此區查看自己房間。

按「繼續」時，API 要求新鮮的 GameServer MR 暫停快照，且快照已接受最新場次序號。存活玩家需要本次入場的有效追蹤，已由戰鬥紀錄確認淘汰的玩家可留在名冊。未通過檢查時，場次保持暫停。獨立房間由有權限的房控或主控繼續，全連線場次由主控繼續。

暫停中的參戰快照另回傳 `mrResumeState`。繼續失敗回傳 HTTP 409 與 `mr-resume-readiness-required`。已接受的同一繼續命令可重試取得原回條。 [驗證紀錄](PROGRESS.md#2026-11-09-mr-暫停後恢復追蹤)

## 五房總覽

控制台 0.31.6 在使用中的房卡顯示名冊人數、有效姿態及合成／追蹤各自的人數。主控可同時查看五房。房控只收到自己房間的摘要，即使場次使用五房連線模式。

`GET /api/rooms/readiness` 回傳 `version: 1` 和可讀房間的摘要。每房包含場次識別、序號、名冊人數、兩種姿態數與來源新鮮度。五房共用一個場次時，服務以同一份已接受的快照分房計數。彙整沿用參戰快照的 admission、席位、健康、連線與姿態判定。摘要沒有個別玩家資料。

總覽頁可見且有使用中的房間時，每秒最多查詢一次。畫面核對房間、場次、序號與名冊人數。超過原本的 1.5 秒新鮮度門檻時撤下有效人數。讀取失敗、換頁或登出也會清除有效狀態。開始與結束仍由操作員決定。

Windows 三包整合可加上 `--check-room-readiness` 核對兩種模式的實際房間計數，再加 `--observe-closure-ui` 檢查新版控制台的房卡與封存。 [三包測試方式](WINDOWS_SERVER_PACKAGE.md#三個可攜包整合驗證)

本機三包測試在五房獨立與五房連線各驗證 25 個模擬玩家，兩種模式的 API 摘要均為每房 5 筆有效合成姿態。瀏覽器也實際顯示五個獨立房間的總覽。追蹤人數的瀏覽器呈現以測試回應驗證，頭盔實機仍待。 [開發進度](PROGRESS.md)

### 五房追蹤驗收開場

控制台 0.31.196 在全館開場清單顯示各房目前核對到的錄製來源 `GameServer` 或 `Simulation`。來源隨原場次及名冊版本核對，快照過期時會隱藏。席位是否有有效追蹤仍由各房的席位和追蹤數量顯示。

控制台 0.31.163 可從「全館場次控制」各房開場狀態按「查看名冊」，直接查看該房玩家及即時參戰快照。五房合併時會篩選到該房，可用「名冊房間」切回全部房間。重新整理同一場次會保留篩選。開場條件仍以原全館檢查為準。

控制台 0.31.164 的名冊人數與即時參戰摘要會跟隨房間篩選。名冊人數以該房的 5 席為上限，姿態有效人數以該房已登記的人數為分母，並沿用 1.5 秒的快照新鮮度。切回全部房間即可查看全場人數。

控制台 0.31.179 在全館命令送出後若發現原場次版本已變更，會列出受影響的房號。獨立場會指出變更的房間，合併場若共用場次版本已變更則列出五房。整批命令遭拒後，請重新整理並核對開場條件，再確認一次。

Windows 三包整合驗證可使用 `--prepare-independent-set --check-venue-begin --check-venue-end --check-venue-launcher --check-venue-participation-gate --check-venue-roster-ui`。兩種模式各由 25 個同機玩家端送出實際合成姿態。Chromium 在開場前逐房操作名冊捷徑，核對原入場、房間、席位及有效姿態。 [三包整合驗證](WINDOWS_SERVER_PACKAGE.md#三個可攜包整合驗證)

控制台 0.31.65 的主控可在「全館場次控制」勾選「五房開場須各有 5 席追蹤就緒」。適用於五房合併及各房獨立，包括同時有 VR 和 MR 的五個獨立場次。名冊未滿、仍有合成姿態或原快照未確認時，畫面顯示各房等候原因。勾選後，五房須同時是本次準備中的目標，且每房的五席均有有效追蹤。新登入預設使用一般開始條件。

操作員確認開始時，管理服務依原場次及序號重新核對最新已接受快照。任何一房未通過時，整批維持準備中。程式介面在 `POST /api/venue/phase` 的 `Begin` 本文加入 `requireFullTracking: true`。接受回條保留此值，重試須帶同一請求識別及原選項。MR 來源仍須符合 Quest 3 設定及原 MR 開場條件。

此選項核對遊戲伺服器接收的追蹤姿態。實體裝置、對位、操作與跨機人數仍依現地驗收。 [混合場館部署](QUEST3.md#混合-vr-與-mr-五房部署包)

### 五房各 5 席有效姿態開場

管理包 0.31.78 在「全館場次控制」提供「五房開場須各有 5 席已連線且姿態有效」。獨立或合併模式都要涵蓋五房，每房五席。VR 可使用有效的合成或追蹤姿態，MR 仍按原條件核對 Quest 3 追蹤。此選項與全追蹤開場擇一，登入時預設一般開場。

各房會列出名冊和有效姿態數。送出後，管理服務依最新已接受的準備中快照再次核對原入場、房間、席位與連線。任一房缺席、姿態無效或快照過期，整批保持準備中。

自動化客戶端可在新版的 `POST /api/venue/phase` 加入 `requireFullParticipation: true`。以回條的同名欄位確認政策已套用。成功時原 `Begin` 事件的 `venue.participationFrame` 保存來源、世界格和擷取偏移。重試須使用同一請求識別與相同政策。

### 執行中五房追蹤總覽

主控專用的「執行中五房追蹤」在控制台 0.31.106 顯示共同取樣時間、各房已確認追蹤的席數及原畫格號。合成、待確認、淘汰及未編列的席位分開列出，準備、暫停及空房也有各自狀態。總數顯示有確認資料的房間數。

主控的 `/api/rooms/readiness` 用同一時間取樣，並在確認讀取期間的場次版本一致時回傳 `trackingSampledAtUtc`。每個可確認的房間附 `venueTracking` 與 `trackingWorldSequence`。獨立場各自核對來源，合併場共用同一張快照。天氣與戰績更新可沿用原名冊和執行階段的有效追蹤，重新繼續或更換名冊後則須等待遊戲端同步。瀏覽器將請求耗時納入 1.5 秒期限，過期後撤下該房的確認席數、畫格號及回放按鈕。房控仍只收到本房資料。

若原畫格記錄到席位姿態中斷，可在該房的總覽列按「檢視姿態中斷快照」。觀戰畫面會停在同一場次、房間與原畫格，並標示中斷席位。需要回到同一房的即時觀戰時，按「返回即時觀戰」。

總覽供場中操作使用。戰後要核對五房在同一段時間持續追蹤，使用原封存錄製與玩家日誌。 [封存核對](EXTERNAL_CLIENTS.md#核對-25-席同時連線的區間) · [驗收紀錄](PROGRESS.md#2026-11-10-執行中五房追蹤總覽)

### VR 房卡的席位提示

控制台 0.31.49 在準備中及執行中的 VR 房卡顯示「入場待同步席位」、「姿態待確認席位」及「已淘汰席位」。等候席位以橘色提示。淘汰席位另列，房卡有效姿態分母按存活名冊計算。姿態待確認可由連線或姿態中斷引起，進入場次即可查看各席快照。

#### 從 VR 房卡暫停檢查席位

管理包 0.31.82 在執行中的 VR 房卡提供「暫停本房檢查席位」。最新有效畫格須已觀察到目前執行階段，且有原入場的席位明確失去連線或有效姿態。仍在同步名冊、等待來源或已淘汰的席位依原狀態顯示。

獨立場由本房房控或主控確認後只暫停該房。五房合併場由主控在受影響的房卡確認後暫停全場。管理服務在同次命令中重新核對場次序號和中斷席位。確認期間席位若已恢復，管理服務會拒絕原暫停要求。

接受後，房卡先顯示「VR 暫停待確認」。原錄製觀察到該暫停命令並送回有效暫停畫格時，才顯示「VR 暫停已套用」。合併場的房卡均會標示觸發的原房號。

程式客戶端可在場次命令本文中加入 `vrParticipationRoomId`、`expectedSequence` 及 `action: "Pause"`。無目前有效中斷證據時回傳 HTTP 409 與 `vr-participation-pause-no-witness`。已接受的命令使用原命令識別及相同本文重試。

#### 從 VR 房卡確認恢復並繼續

管理包 0.31.83 在因席位中斷而暫停的房卡列出各房等候席位。遊戲端須先送回符合最新場次序號的有效暫停畫格，並確認目前名冊內所有存活席位都有可參戰姿態。只要合併場有任一房仍有等候席位，原觸發房的繼續按鈕就會保持停用。

確認恢復後，獨立場由本房房控或主控按「確認恢復後繼續本房」。合併場由主控在原觸發房按「確認恢復後繼續五房」。管理服務於按下確認後重新檢查最新畫格。若原席位又失去姿態或畫格已過期，場次會保持暫停。一般場次控制送出的 `Resume` 也經過相同檢查，未就緒時回傳 HTTP 409 與 `vr-participation-resume-not-ready`。其他方式觸發的 VR 暫停沿用原操作流程。

房卡依最新管理階段及原入場識別比對已接受的世界快照。`/api/rooms/readiness` 在確認來源後提供 `vrParticipation`，其中席位由 1 起算。來源過期、場次變更或等待套用開始及繼續時，先撤下舊席位提示。房控只會收到本房資料。 [五房驗證](PROGRESS.md)

API／控制台0.29新增名冊旁的「即時參戰快照」與有效人數。操作員可以直接區分已登記的頭盔分類、已接受世界中的有效姿態，以及等待來源／姿態中斷；不必只看名冊人數推斷玩家是否在場。

這是**已接受快照的參戰觀察**。Simulation 明確顯示合成姿態，Tracked 表示該份來源提交追蹤資料。VR 開始、暫停與結束仍沿用原控制政策。MR 開場另使用本頁的名冊和快照檢查。

## 操作與狀態

登入主控或房間控制台，選取場次。在「玩家名冊」每位玩家旁查看姿態狀態；摘要顯示來源與有效人數。只在房間與場次頁且頁面可見時，約每秒讀一次診斷，每250ms更新本地老化顯示；不傳送頭手座標或逐幀輸入。

| 顯示 | 意義 |
|---|---|
| 等待遊戲來源／第一份快照 | 名冊或header已存在，但未有可用世界幀 |
| 姿態有效 · 合成／追蹤姿態 | 同一次入場、存活、connected且來源時間有效的最後已接受身體 |
| 等待本次入場同步 | 同一playerId已重新入場，但舊frame觀察的admission／房間／席位不符 |
| 姿態未就緒／中斷 | 該入場的身體未connected或沒有可用頭手來源 |
| 已淘汰 | 保存健康已為0，不視為有效參戰 |
| 快照已過期／擷取時間未知／來源時鐘未同步 | 不以收到時間或心跳補造新鮮度 |
| 等待階段同步／管理連線中斷 | 來源階段尚未追上管理，或來源明確suspended |
| 場次已結束 | End立即優先；舊的有效身體不再顯示為參戰 |

來源年齡使用原header.captureStartedAtUtc＋最後packet.elapsedMilliseconds，相對API抽樣時間計算；保留既有超前1000ms／過期1500ms邊界。瀏覽器再從**請求開始**計算performance單調經過時間，包含下載等待，沉默超過門檻即移除綠色；不是拿HTTP回應抵達時間重設來源時鐘。這是保守觀察，不是RTT、網路延遲或FPS。

暫停中的玩家仍可有有效姿態，畫面同時顯示場次已暫停；有效姿態不表示正在射擊。失聯、切頁、換場或登出會取消／隔離舊請求；場次epoch、登入epoch與current admission／room／seat均須相符，舊回應不能恢復綠色。UI管理序號已較新時，舊readiness報告只顯示等待更新。

## API與保存邊界

`GET /api/sessions/{id}/readiness`僅Master／可讀此場次的RoomController；逐次傳遞已認證Actor並檢查房間範圍，GameServer及Internal也不當控制台使用。Linked讀取沿用既有場次讀取政策，不改玩家操作的房間權限。

回傳version1、sessionId／sessionSequence、sampledAtUtc、sourceState／origin、worldSequence／observedSequence、capturedAtUtc／sourceAgeMilliseconds及當前名冊的playerId／admissionId／roomId／seat／state／rigKind／canParticipate。沒有座標、票券或主控／GameServer key。每份報告只代表其sessionSequence與抽樣時點；管理與來源可能在下一瞬間改變，不能拿它授權玩家戰鬥。

WorldRecordings在自己的gate下讀最後已接受幀，並以SessionManager.Observed還原該幀真正看到的名冊，與本次管理快照比對admission／room／seat。重新加入同一playerId，即使舊frame仍新鮮且connected，也不得沿用舊身體。僅讀現有資料，不追加事件、修改投影、改舊header、補造舊擷取時間或新增DB schema。envelope7、world schema1、rules0.8.0及原素材pin保持；既有新格式reader限制不變。

Unity仍0.31.0／code38／NGO29及原雙平台receipt，本輪不改遊戲wire／追蹤／入場政策，不重新建置或宣稱新的141項Editor結果。部署API／UI0.29需一起更新；工具的版本gate同步，避免新版控制台對舊API讀不存在的狀態。

真正原生整合入口：

```powershell
python scripts/check-desktop-readiness.py --runtime-root "$env:LOCALAPPDATA/VrCommand/SimulationRuns" --api-dll <本次隔離API.dll>
```
