# 主控台任務收尾

## 回看單場 VR 追蹤開場

使用管理包 0.31.201 從單場控制按「確認追蹤並開始」時，管理服務會保存當時採信的準備畫格。任務結束且戰鬥統計與世界回放已封存後，在「任務收尾」按「回看本場追蹤開場」。獨立場顯示原房間俯視，主控可查看合併場的全部房間。操作員可逐格查閱，並用「回到原開場畫格」重新定位。

回放會重新核對原遊戲串流、開場前的管理序號、擷取偏移及當時已連線的追蹤名冊。房間再開新場或玩家在任務中離開時，仍使用原開場的錄製與名冊。開場時須有保存畫格指標，0.31.200 先前已開場的紀錄可用一般回放查閱。 [開場操作](PLAYER_READINESS.md#單場-vr-追蹤開場)

管理包 0.31.202 中，符合單場驗收匯出條件的場次會在「下載場館驗收資料 ZIP」附上原開場資料。可保留整包，再用同場的原生回放檔離線核對。 [離線操作](EXTERNAL_CLIENTS.md#用單場-zip-核對追蹤開場)

## 離場玩家戰績

管理包 0.31.203 可在單場驗收 ZIP 保存結束前被移出的玩家及其封存戰績。匯出會附原入場與移除序號，離線核對時需同一場的戰鬥和世界日誌。 [核對離場玩家](EXTERNAL_CLIENTS.md#核對任務中被移出的玩家)

管理包 0.31.204 的全館結束批次會顯示各原場次的離場戰績數，並在雙封存後將原入場和離場序號加到該場的驗收 ZIP。可以在房間結束名冊為空時匯出已保存的戰績。含回條的匯出以結束名冊核對送達。 [核對五房批次](EXTERNAL_CLIENTS.md#核對五房批次中的離場戰績)

管理包 0.31.205 起，主控可在原結束批次按「查看離場玩家戰績」，直接查看房號、玩家與封存的耗彈、命中、擊殺、中彈、耗損、命中率、血量。按「個人回放」會停在原場次的封存尾端，並以該玩家及原房間搜尋事件。換批次或離開場次控制會關閉戰績明細。

管理包 0.31.206 可從同一張表下載離場玩家的個人 CSV。下載前會核對原場次、房間、玩家、封存序號及戰績。關閉明細、換批次或登出時，控制台會取消尚未完成的下載。 [個人戰績檔](REPORTS.md#從戰績開啟個人回放)

## 玩家戰績回條

管理包 0.31.109 搭配遊戲 0.50.2。在「任務收尾」等戰鬥統計與世界回放封存後，展開「玩家戰績回條」查看各席。主控看整場名冊。房控在合併場也只看自己房間的席位。

已確認表示原遊戲伺服器收到了該次入場連線的戰績回覆，並已存入管理服務。分母是任務結束時的名冊。玩家提前離開、未接收戰績或回條未能送到管理服務時，畫面都維持「未確認」。可從同一場次選取玩家並下載已封存的戰績 CSV。 [戰績匯出](REPORTS.md)

遊戲伺服器核對原網路連線、玩家及入場識別後，才送出回條。管理服務再核對原戰鬥來源、戰鬥封存、世界封存、終止名冊和統計序號。成功回條可重送，管理服務重啟後仍可讀取。回條不影響戰績、回放、CSV 或遊戲伺服器原有收尾時間。

操作員可用 `GET /api/sessions/{id}/world?includeDebriefReceipts=true` 取得所屬範圍的狀態。原戰鬥來源用 `POST /api/sessions/{id}/debrief-receipts` 提交原入場的確認，成功回傳 HTTP 204。舊場次沒有保存過的回條時，名冊席位皆顯示「未確認」。

## 全館批次結束

Windows 管理包 0.31.34 起，主控可在「全館場次控制」按「結束全部未結束場次」。確認視窗列出房號及場次數，包含準備中、執行中及暫停中的場次。五房合併只對同一場提交一個命令。確認後，管理服務以同一筆交易保存全部結束命令。若有場次在預覽後新增、結束或切換階段，服務會拒絕整批並要求重新確認。

管理端記錄結束後，房間可供新場次使用。「最近一次全館收尾」仍指向原場次，分別顯示戰鬥統計與世界回放的封存狀態。按「查看場次」可開啟原紀錄。重新登入或重啟管理服務後可讀取同一批結果。資料封存完成後，遊戲伺服器仍需完成玩家戰績傳送與收尾。

管理包 0.31.37 起，戰鬥資料全部完成後可從同一區下載本批戰績 ZIP。 [戰績匯出](REPORTS.md#下載全館結束批次)

管理包 0.31.38 起，可從同一表直接開啟原場次回放或已保存片段。 [觀戰與回放](WORLD_RECORDING.md#從房卡或全館收尾開啟)

管理包 0.31.93 可在同批獨立房間間保留目前擷取時間，方便比較兩房同一時段的原錄製。 [同批回放對齊](WORLD_RECORDING.md#對齊同批獨立房間的回放)

管理包 0.31.110 的「戰績回條」欄逐房顯示已確認席數與結束名冊席數。合併場仍分列五房。尚未封存的房間顯示「等待雙封存」，從未連結遊戲來源的房間則另列狀態。歷史批次仍以原場次計算，管理服務後續收到回條時會更新。按「查看場次」可查個別玩家。批次讀取可加上 `includeDebriefReceipts=true` 取得各房席數，限主控使用。

### 從全館收尾查看席位

管理包 0.31.132 在完成戰鬥與世界封存且有玩家的房間提供「查看席位」。主控可在所選結束批次查看房號、席號、玩家與回條狀態，或勾選「只顯示未確認」。明細開啟時，該房摘要收到新的確認便會嘗試更新。若出現讀取錯誤，可按「重新讀取」。

明細對應原結束批次與封存時的名冊，房間重新開場後仍可查閱。切換批次、離開操作頁或登出會關閉明細。主控可透過 `GET /api/venue/closure/{id}/rooms/{roomId}/debrief-receipts` 讀取該房原席位，回應為 `no-store`。房控仍可從單場「任務收尾」查看本房回條。

管理包 0.31.133 在每個席位提供「下載 CSV」。若玩家尚未收到遊戲內戰績，可用該席的原封存檔人工補發。檔案和從原場次下載的個人戰績相同，回條狀態仍由原遊戲伺服器確認。切換批次或房間會取消未完成的下載。 [個人戰績](REPORTS.md#從戰績開啟個人回放)

管理包 0.31.136 的同一張表可查看每席原封存的耗彈、命中、擊殺、中彈、耗損、命中率與血量。「只顯示未確認」會保留這些席位的戰績及下載。手機可在表格內左右滑動。既有席位端點加上 `includeScores=true` 時會隨每席回傳 `score`，數值取自同一場次的最終戰鬥報表。 [全館分房戰績](REPORTS.md#在全館收尾比較分房戰績)

管理包 0.31.137 起，在原批次「查看席位」按該席的「個人回放」，即可停在該場次封存的最後一格，並搜尋該玩家在原房間的事件。若第一段搜尋沒有符合的事件，可按「繼續搜尋」。未確認回條的玩家也可回看。從觀戰頁返回「場次控制」後，仍可在所選批次重新開啟席位明細。主控可在同一席位端點加上 `includePlayerIds=true` 取得原名冊的 `playerId`。 [個人回放](REPORTS.md#從戰績開啟個人回放)

管理包 0.31.241 從全館、分房席位或離場戰績開啟個人回放時，可按「返回原批次戰績」。主控台會重讀原批次與封存明細，恢復原房間或全館範圍及「只顯示未確認」設定。玩家仍在清單時，焦點會回到該列。即使已有較新的結束批次，也會返回原紀錄。換到另一段錄製時會關閉這個返回入口。

### 查看全館未確認席位

管理包 0.31.149 在所選「全館收尾」批次提供「查看全館未確認席位」。主控可依房號和席號查看所有已雙封存房間的未確認玩家，直接下載各席原 CSV 或開啟原房間的個人回放。取消勾選「只顯示未確認」即可核對已確認的席位。

清單的席數來自可讀取回條的原房間。若有名冊的房間仍無可核對的回條，畫面會列出房號。開啟清單後，當管理台收到同一批次的新封存或回條，會更新顯示。批次切換後請重新開啟清單。房控仍可在單場「任務收尾」查本房回條。

管理包 0.31.224 在席位明細提供「下載未確認清單 CSV」。全館清單須先核對所有有名冊的房間，單房清單則使用該房已核對的回條。檔案只列出下載當下畫面資料中的未確認席位，包含原場次、房席、管理與戰鬥及世界序號，以及原封存的個人戰績。玩家後來確認時，重新匯出的清單會排除該席。若全數確認，下載按鈕會停用。

`GET /api/venue/closure/{id}/debrief-seats` 限主控，從同一次查閱回傳原批次各已雙封存且有席位的房間。每房包含原錄製識別、封存界線、玩家識別與戰績，回應為 `no-store`。

若送出後回覆遺失，可重試確認原批次。管理端 `GET /api/venue/phase` 提供 `end` 預覽，`POST /api/venue/phase` 使用 `action: "End"`、原 `sessionId` 與 `phaseSinceSequence` 及同一個 `Idempotency-Key`。`GET /api/venue/closure` 提供主控最近一次依保存時間排序的批次，含各原場次的房號、結束序號、戰鬥及世界封存狀態。個別場次結束時仍可從本場的收尾面板追蹤。

保存全館批次結束紀錄的管理資料庫須由 0.31.34 或更新的管理包開啟。

## 歷史批次

Windows 管理包 0.31.39 起，在「全館收尾」按「載入批次清單」。批次按結束時間由新到舊顯示，包含原房號、任務名稱及批次識別前八碼。每次讀取 20 筆，按「載入更早批次」可繼續查閱。

選取較早的批次後，可從同一表開啟各房原場次、回放或已保存片段，並在戰鬥資料可匯出時下載該批戰績 ZIP。更新清單、房間重新使用或另一批場次結束時，畫面會保留所選批次。要回到持續追蹤最新收尾，請選「自動顯示最新批次」。

主控可用 `GET /api/venue/closure/history?limit=20` 讀取清單。若回傳 `nextBefore`，下一頁以 `before` 帶入同一批次識別，從該批之前開始。每頁接受 1 至 50 筆。以 `GET /api/venue/closure/{id}` 讀取原場次和各自的封存狀態，房控無權讀取全館清單或批次明細。

### 下載本批場館驗收

Windows 管理包 0.31.40 起，主控可在全館收尾按「下載本批場館驗收 ZIP」。各原場次都須曾開場、完成戰鬥及世界雙封存、公布端點，且結束名冊與統計相符。缺件時畫面列出對應房號。選取歷史批次時會依該批條件匯出。

ZIP 內的 `closure.json` 保存原批次明細。每場另有一份 ZIP，包含原名冊、統計與公告端點，內容與從單場收尾下載的驗收 ZIP 一致。五房合併使用 `linked.zip`，獨立場使用 `room-01.zip` 等房號檔名。請私下保管原 ZIP，並在驗收清單的 `venueBundle` 直接指定這份原檔，另備啟動器終止報告及原伺服器與玩家日誌。 [五房 25 席操作](EXTERNAL_CLIENTS.md#一次核對五房-25-席)

`GET /api/venue/closure/{id}/field-evidence.zip` 依原批次識別讀取，回應為 `no-store`，限主控。任一原場次資料缺件時回應 409，並附待處理的房號。

### 下載驗收 ZIP 與全員回條

管理包 0.31.158 起，待所選批次的場館驗收資料齊備、原名冊席位全數確認後，可按「下載驗收 ZIP 與全員回條」。若仍有缺件，按鈕旁會列出待處理的房號。主控可在歷史清單選取原批次，房間重用後仍可下載原場資料。

合併檔保留原 `closure.json`、各場驗收 ZIP，並加入 `debrief-receipts.json`。將它直接填入 `venueBundle`，離線驗收工具會使用內附回條核對原批次、場次、名冊與封存尾界。合併檔含入場識別，請私下保存。 [離線驗收設定](EXTERNAL_CLIENTS.md#一次核對五房-25-席)

主控可在原下載端點加上 `?includeDebriefReceipts=true` 取得合併檔。原場館驗收 ZIP 與獨立回條 JSON 仍可分開下載。若雙封存已完成而有席位未確認，合併下載回應 409 與 `venue-field-receipts-not-confirmed`。

### 下載本批戰績回條

管理包 0.31.111 起，選取原批次並等每場完成戰鬥與世界封存，再按「下載本批戰績回條 JSON」。檔案保存當下各席的確認狀態、入場識別和原封存序號。若有未確認席位，可以等回條到達再下載。原場館驗收 ZIP 維持原內容。 [離線驗收設定](EXTERNAL_CLIENTS.md#一次核對五房-25-席)

主控也可用 `GET /api/venue/closure/{id}/debrief-receipts.json` 下載同一份資料，回應為 `no-store`。檔案含場次與玩家入場識別，和驗收 ZIP 一併私下保存。

從 0.31.66 開始，符合五房追蹤開場條件的原場次會在 `closure.json` 保留 `trackingBegin`，列出開始批次、管理序號、世界來源及原準備中畫格。可與本次封存的原 `.worldlog` 核對。 [開場錄製核對](EXTERNAL_CLIENTS.md#核對五房追蹤開場錄製)

管理包 0.31.79 也會把「各有 5 席已連線且姿態有效」採信的原畫格列在 `participationBegin`。主控下載的場館驗收 ZIP 會帶上同一欄位。 [25 席有效姿態核對](EXTERNAL_CLIENTS.md#核對五房有效姿態開場)

### 回看追蹤開場

控制台 0.31.67 的「全館收尾」提供「回看追蹤開場」。選取原結束批次，在對應場次按下按鈕，回放會停在管理服務採信的準備中畫格。五房合併顯示全場，獨立場顯示原房間的俯視。可用前一格與下一格查看已保存的相鄰畫格。

按鈕需要批次中有原畫格指標及可讀錄製。控制台依原開場紀錄核對錄製來源、房間、開始前管理序號、擷取偏移及每房有效追蹤人數，再顯示該格。0.31.237 的 5／10 席試場沿用開場保存的 `playersPerRoom`，既有全館紀錄按每房五席核對。回放顯示錄製設定，各玩家實際保存的頭手姿態來源可在角色資訊查看。 [離線驗收](EXTERNAL_CLIENTS.md#核對五房追蹤開場錄製)

### 回看有效姿態開場

使用「五房開場須各有 5 席已連線且姿態有效」的場次，可在管理包 0.31.80 的全館收尾按「回看有效姿態開場」。播放會停在原採信的準備中畫格，分列當格的追蹤及合成席位。獨立場使用原房俯視，合併場使用全場視角。按上一格或下一格可查看相鄰的保存畫格。

### 比較準備與執行畫格

管理包 0.31.161 的主控在「回看追蹤開場」或「回看有效姿態開場」進入錄製後，可按「跳到首個執行畫格」。控制台會在目前已確認的保存範圍內，找出第一個已套用原開始指令、遊戲刻數已前進且來源未暫緩的執行中畫格。按「回到原開場畫格」可再次查看原準備中畫格及當格席位。兩個按鈕均保留原錄製、房間與鏡頭。

若已保存的片段尚未出現符合條件的畫格，或回應與原開場指令及錄製不符，會保留目前畫面。此功能使用主控唯讀的 `GET /api/sessions/{id}/world/venue-begin-running`，查詢以 `throughFrame` 限制於已保存的尾端。

控制台會核對原錄製來源、房間、管理序號、擷取偏移及開場紀錄保存的每房席數。VR 的有效姿態政策可使用合成與追蹤，MR 畫格須為 Quest 3 設定下的有效追蹤。已封存錄製與仍在等待封存的可讀片段均可使用。 [離線驗收](EXTERNAL_CLIENTS.md#核對五房有效姿態開場)

## 場次切換與操作

控制台 0.31.5 會保留操作當下的場次識別。若背景更新期間，另一位操作員已結束原場次而使它離開清單，控制台會清空選取並隱藏原操作區。請明確選取要操作的場次。若要查看原場次的封存資料，可勾選「包含已結束紀錄」後重新選取。

開始、暫停、繼續、結束、環境、敵軍、任務時鐘、名冊與配票都會在送出前核對原場次。由本頁結束的場次仍會保留並顯示封存進度。已送出但回應遺失的命令，仍依原 UUID 與序號重試。

## 操作與狀態

控制台 0.31.10 在場次結束後顯示同一來源已接受的戰鬥筆數及已保存的錄製格數。兩項各自核對，資料無法確認時會清除對應數量。若遊戲伺服器提前退出，可到「觀戰與任務回放」查看已保存片段，封存狀態仍分開顯示。 [回放已保存片段](WORLD_RECORDING.md#回放未封存的已保存片段)

Preparing時提示先啟動本場遊戲伺服器、加入玩家、交付各自的連線檔，再開始任務。Running／Paused時只提示結束後確認資料，不把目前的姿態、來源或程序狀態當成封存完成。

End後，戰鬥統計需要同場次、精確目前管理序號、明確pendingTelemetry=false及原combatStream.sealed=true。世界回放需要服務回傳complete=true、正數acceptedSequence，以及同session／stream／origin／房間與任務時鐘能力；舊clock0仍可讀。這裡信任既有world seal契約：API已核對最後Ended幀、原combat尾界與最終統計。前端沒有重新驗證全回放，也不讀local journal或SQLite。

## 讀取與隔離

只在房間與場次頁可見、目前登入且選中Ended／有來源場次時，每兩秒最多一次GET world，單次五秒逾時。依epoch／key／actor／場次／序號／stream與generation隔離回應；選取、登出、切頁、隱藏頁面或未確認命令會清除舊狀態，背景更新失敗也使封存未確認。新的成功場次刷新才可解除該失敗狀態。401走原登出流程；403／5xx／斷線不沿用舊綠色。沒有增加寫入、重試End或變更0.5／1.5秒參戰政策。

已確認的End會保留目前場次並勾選「包含已結束紀錄」。原先只對尚未combat seal的回條如此處理，若End回應遺失、手動重試時已seal，畫面會把Ended場次篩掉。現在只要同一End回條確認Ended便保留，包含已封存的duplicate；命令UUID／expectedSequence與原手動重試流程保持。
