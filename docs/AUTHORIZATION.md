# 控制台身分與權限 v0.4

目前使用分別配發給控制台的 Bearer 憑證。認證結果由伺服器設定決定，不接受請求 body 裡自行宣告的身分或角色。這是原型的控制台認證，還不是員工個人帳號、頭盔註冊或企業登入。

| 身分 | 讀取 | 可變更 |
|---|---|---|
| Master（`master`） | 全館任務、房間、活動與歷史場次 | 共用任務、五房名額、獨立／全連線場次與所有管理命令 |
| Room1–Room5（`room-1` 等） | 任務庫、自房名額、自房獨立場次、包含自房的全連線場次 | 僅自房獨立場次的建立與管理命令；獨立／全連線中的本房玩家名額 |
| GameServer（`game-server`） | 全館任務、房間、場次與統計 | 僅 `/combat` 戰鬥事件接入；沒有管理寫入權限 |

全連線場次的場景、玩家與事件屬於共享世界，包含自房的房間控制台可以讀取完整共享場次；只有主控能發出影響整場的開始／暫停／環境／敵軍等命令。房間控制台可加入／移除自己的玩家，不能操作其他房間的名額。其他獨立房間的快照與事件回傳 403，列表會濾除。

所有 `/api` 路徑皆要求 `Authorization: Bearer <credential>`。`/` 與 `/health` 公開；`GET /api/me` 回傳經驗證的控制台 ID、角色與可選房間編號。缺少或錯誤憑證回傳 401；身分有效但權限不足回傳 403。憑證本身不出現在快照、事件或錯誤訊息中。

## 設定

Windows 本機：在根目錄執行 `scripts/start-local.ps1`，自動產生 `data/operator-keys.local.json` 並啟動服務。預設只監聽 `127.0.0.1:5080`，可用 `-Port 5081` 換埠。憑證檔以一般 JSON 存放於本機，依賴主機的檔案存取控制；不應提交到 Git 或散發整份檔案給每個控制台。

部署可透過下列環境變數設定，不必使用本機助手：

```text
OperatorKeys__Master
OperatorKeys__Room1
OperatorKeys__Room2
OperatorKeys__Room3
OperatorKeys__Room4
OperatorKeys__Room5
OperatorKeys__GameServer
```

每份憑證需要 32–512 個非空白字元，應由安全亂數產生。Master 必須設定；未設定的房間或 GameServer 無法登入。重複憑證、短憑證與未知設定名稱會使啟動失敗，不退回匿名模式。可由命令列 `--OperatorKeyFile <絕對 JSON 路徑>` 載入 `{ "OperatorKeys": { ... } }` 檔案；環境變數及命令列設定優先於檔案。

換鑰需更新設定並重啟 API；重啟後舊鑰回傳 401，控制台 ID 不變，原命令的去重仍可使用。這不是即時撤銷或可到期的登入工作階段。未加入 TLS、速率限制、個人帳號與身分供應商，跨機部署應先完成這些部署能力。

## 事件與復原

新事件使用 envelope schema 3，保留 schema 2 引入的 `actor: { id, role, roomId }`。角色與房間權限在操作前及從歷史復原時都會檢查；同一控制命令或戰鬥報告 ID 的重送必須由同一來源身分發出。換鑰仍屬同一身分，可以原樣重送。主控及房間控制台不能提交戰鬥事件；模擬器使用 GameServer 憑證且將資料明確標記為 Simulation。

schema 1 歷史保持 `actor: null`，不補造控制台身分；由受信任的舊版內部操作復原。舊版已接受的命令無法改由新認證身分接管去重 ID，回傳 409。核心函式庫另有 `Internal` 身分供受信任的程序內部呼叫與舊歷史使用；HTTP 認證永遠不配發此角色。

事件檔案尚未加簽或接入外部不可變稽核儲存，因此只能視為應用程式操作紀錄。已認證的 ID 證明使用哪份控制台憑證，不能辨識共享控制台後方的自然人。
